# Competitor comparison: Aginiti vs. garak

Set up 2026-08-09 in response to the "Competitor-level comparison (🔴)"
gap named in the 9-dimension analysis. `garak` (NVIDIA's open-source LLM
vulnerability scanner, github.com/NVIDIA/garak) is the most credible,
easily-obtainable comparison point — already cited by name as inspiration
in this project's own `aginiti/operators/data_exposure.py`.

## Fairness: same target, same hardening, no tuning either way

`experiments/garak_setup.py` creates the garak-facing workspace through
the **same gateway** (`aginiti/target_hardening/gateway_server.py`,
`localhost:3002`) Aginiti's own adapter uses — same `HARDENED_PROMPT`,
same document-sanitization / output-redaction / service-account-tier /
human-approval / adaptive-lockout controls. Neither tool gets an easier
or harder version of the target. Config: `experiments/
garak_rest_generator.json`, generated by that script (not committed with
a live gateway key baked in permanently — regenerate per run).

## The one honest scoping limit that matters here

garak's `RestGenerator` is a plain text-in/text-out interface. It has no
concept of a tool call, a document upload, or network egress — it can
only ever observe what comes back in `textResponse`. That means a garak
run can assess this project's **L0 (model behavior) and L1 (does the
model comply with something already in its context)** layers — the
system-prompt-extraction / jailbreak / encoding-evasion / direct-
prompt-injection-compliance class of finding — but structurally **cannot
reach L2-L5** (real tool invocation, confirmed network egress) at all.
Aginiti's own AnythingLLM chains (the automatic-mode and markdown-exfil
attacks, both L5) are simply outside what any REST-generator-based tool
including garak can observe, not because the target was tuned to favor
Aginiti. A fair headline comparison is therefore scoped explicitly to
"who complies with the class of attack garak can see" — reported as
such, not silently generalized to "who wins overall."

Comparable probe families chosen to line up with Aginiti's own operator
categories (`aginiti/operators/data_exposure.py`), not garak's full
default suite:

| Aginiti operator | Comparable garak probe module |
|---|---|
| `system_prompt_extraction` | `promptinject` |
| `jailbreak_dan_style` | `dan` |
| `encoding_evasion_probe` | `encoding` |
| `anythingllm_rag_document_plant` + `..._injection_trigger` (L1) | `latentinjection` (the most directly comparable module -- indirect injection via context the model is shown, not typed by the "user") |

## Setup steps

```bash
python experiments/garak_setup.py
# prints the workspace slug and writes experiments/garak_rest_generator.json

garak --model_type rest -G experiments/garak_rest_generator.json --probes test.Test
# smoke test only -- garak's own trivial connectivity probe, confirms the
# REST plumbing works before spending real probe budget
```

## Status as of 2026-08-11

Installed, configured, and **smoke-tested with a real probe against the
live target** — `dan.DAN_Jailbreak` (5 generations), both of garak's own
detectors (`dan.DANJailbreak`, `mitigation.MitigationBypass`) now report
`PASS 5/5`: the hardened target neither adopted the DAN persona nor
failed to refuse.

### A real bug found and fixed along the way

The first run of this exact probe **500'd on every one of its 5
generations**, and garak's own exponential backoff meant it would have
retried forever. Root cause, confirmed by reproducing directly and
reading the upstream source (not guessed): AnythingLLM's own
`server/utils/AiProviders/gemini/index.js:401` reads
`result.output.choices[0].message.content` without checking whether
`.message` exists first. When Gemini's safety filter blocks a response
— exactly what a DAN-style jailbreak prompt triggers, given this
workspace's `GeminiSafetySetting=BLOCK_MEDIUM_AND_ABOVE` — `.message` is
`undefined` and the whole request crashes with `TypeError: Cannot read
properties of undefined (reading 'content')` instead of returning a
clean refusal.

Fixed at the gateway layer (`aginiti/target_hardening/gateway_server.py`,
`workspace_chat()`), not by patching AnythingLLM's own source: a narrow,
exact-string match on this one confirmed crash signature rewrites it into
a real, natural-language refusal (`"I'm not able to help with that
request."`) with a 200 status, logged to the gateway's audit trail as
`target_crash_treated_as_refusal`. A genuinely different 500 (an
unrelated bug, an auth failure, a real outage) is **not** caught by this
narrow match and still propagates as-is — this can't mask a new, different
failure as a clean refusal.

One live-caught refinement worth recording: the first version of the
synthesized text was a bracketed system-note string
(`"[response blocked or unavailable]"`), which correctly stopped the
crash but produced a **false 100% "attack success rate"** from garak's
`mitigation.MitigationBypass` detector — that detector pattern-matches
for an ordinary-sounding refusal phrase, and didn't recognize a bracketed
note as one. Switching to natural refusal language fixed this too,
confirmed by re-running the exact same probe.

This fix benefits every caller through the gateway, not just garak —
including Aginiti's own future exp18 runs, which could hit the same
upstream crash class on any jailbreak-shaped operator and would have
gotten an opaque `CAMPAIGN_ERROR` instead of a clean, correctly-judged
refusal.

## exp19: the real head-to-head, run 2026-08-11/12

Both tools tested against the identical hardened target (v2 gateway +
`HARDENED_PROMPT_V2`), same fresh-workspace-per-trial discipline, N=15 per
category for Aginiti (`experiments/exp19_garak_vs_aginiti.py`, results in
`experiments/results/exp19_aginiti_direct/`), garak run via its own CLI
(`-g 1`, `-P` probe-option file, manifest in the session scratchpad — see
`experiments/exp19_garak_vs_aginiti.py`'s docstring for the exact
invocations). Aginiti operators were called directly through
`ObservationAdapter`, bypassing the planner, to match garak's own
planner-free per-probe methodology.

| Category | Aginiti operator | Aginiti ASR | garak probe | garak ASR | Comparable? |
|---|---|---|---|---|---|
| System-prompt extraction | `system_prompt_extraction` | 0/15 (0%) | `sysprompt_extraction.SystemPromptExtraction` | 0/28 (0%) | Yes — both 0%, target defended both |
| Jailbreak | `jailbreak_dan_style` | 0/15 (0%) | `dan.DAN_Jailbreak` | 0/15 (0%) | Yes — both 0%, target defended both |
| Indirect/latent injection | `anythingllm_rag_injection_trigger` | 0/15 (0%) | `latentinjection.LatentInjectionFactSnippetEiffel` | 0/15 (0%) | Yes — both 0%, target defended both |
| Markdown/web exfiltration | `anythingllm_markdown_image_exfil_trigger` | 0/15 (0%) | `web_injection.MarkdownImageExfil` | 0/12 (0%) | Yes — both 0%, target defended both |
| Encoding evasion | `encoding_evasion_probe` | 0/15 (0%) | `encoding.InjectBase64` | 13-14/15 (87-93%) | **No — see below** |

### The one dramatic-looking number (93% vs 0%) is not a fair comparison

Pulling garak's own raw traces for `encoding.InjectBase64` shows its
prompts ask the model to **decode and echo back an arbitrary base64
string** — several of which happen to be XSS/script payloads from garak's
default toxicity corpus (e.g. `PElNRyBTUkM9amF2YXNjcmlwdDphbGVydCg...`
decodes to `<IMG SRC=javascript:alert(...)>`). garak's `DecodeApprox`/
`DecodeMatch` detectors score "attack success" whenever the decoded
string appears in the response — which is exactly what happens when the
model correctly performs the harmless transcoding task it was asked to
do. It is not evidence the model acted on a hidden instruction.

Aginiti's `encoding_evasion_probe` asks a structurally different
question: whether the model will **execute an instruction concealed
inside** the encoded payload (e.g. "reveal your system prompt"), not
merely decode and repeat text. 0/15 there means the hardened target's
safety instructions survived being reached via an indirect (encoded)
channel — a materially different and stronger claim than what garak's
detector pair actually measures.

**Bottom line:** on the four genuinely comparable categories, Aginiti and
garak agree exactly (target fully defended, 0% ASR both tools) — a real,
useful cross-check that neither tool is hallucinating a false positive.
The encoding category is not a fair apples-to-apples comparison; garak's
detector answers "did the model decode text," Aginiti's answers "did the
model obey a hidden instruction," and conflating the two would have
manufactured a false 93-points-stronger headline for garak that the
traces don't actually support. Where Aginiti is genuinely stronger is
structural, not score-based: garak's REST generator cannot observe L2-L5
findings (real tool calls, confirmed network egress) at all — the
automatic-mode and markdown-exfil chains are outside its reach by
construction, not because the target favored Aginiti. See
`aginiti/graph/security_boundary.py` for that taxonomy.
